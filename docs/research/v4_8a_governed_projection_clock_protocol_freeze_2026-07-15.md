# V4.8A governed projection clock protocol freeze

Date: 2026-07-15

Status: implemented and locally verified; not promotion-ready

Roadmap position: Stage 1 critical corrections, after V4.7B and before loaded-chronyd provenance and the real TLS/WebSocket driver

## 1. Outcome

V4.8A closes the projection-clock and live-construction gaps found after the
V4.7B socket/clock authority work.

Every mutation of a governed `PhysicalProjectionStoreV4` now obtains one
typed clock-evidence sample immediately before its SQLite write transaction,
validates it, and freezes that exact sample for every timestamp generated by
the transaction. Cheap same-domain monotonic probes after lock acquisition and
immediately before commit ensure the evidence has not regressed or expired;
they do not create a second wall-clock observation. The sample is consumed
even if the SQL transaction rolls back. A store reopened from disk has no live
clock authority until a new exact owner is bound.

The live Linux construction boundary is also fail-closed:

- a structural test driver cannot create a live owner;
- fake or subclassed journals and writer leases are rejected;
- a forged live-looking object and the private construction token cannot
  create a live runtime;
- a test runtime cannot downgrade a live-bound store or clock authority;
- live construction cannot inject wall-clock or entropy seams;
- the runtime and projection must retain the exact same owner object, not only
  equal clock identifiers;
- caller-authored TLS/WebSocket session facts are rejected by both the runtime
  and the live-bound projection.

This is a local authority and transaction-causality result. It does not prove
that the currently running `chronyd` loaded the reviewed configuration, does
not implement TLS or WebSocket I/O, and does not establish live delivery,
trading safety, predictive edge, or profitability.

## 2. Why this boundary comes before TLS

The alternatives were evaluated against the complete authority chain.

| Alternative | Decision | Reason |
|---|---|---|
| Implement the TLS/WebSocket driver first | Rejected | Authentic handshake observations could still be committed under a caller-controlled projection clock, and a structural fake driver could still enter the nominal live factory. |
| Continue using `datetime.now()` in the projection | Rejected for live authority | It has no signed source, uncertainty, lifetime, boot-domain, or causal-bracket evidence. |
| Sample the governed clock independently for each generated field | Rejected | One logical commit could acquire internally inconsistent receipt, batch, fence, deployment, and authorization times. |
| Persist “live clock bound” in SQLite and restore it on reopen | Rejected | Durable identifiers are not a live process/thread/owner capability; restoring them would manufacture authority after restart. |
| Run `chronyc` while holding the SQLite write lock | Rejected | The external query can block other writers and increase lock duration without improving atomicity. |
| Sample once immediately before `BEGIN IMMEDIATE`, validate, and freeze it for the transaction | Selected | External evidence is collected before the database lock, invalid evidence cannot mutate SQL, and one immutable observation supplies the complete commit chronology. |

The ordering is therefore:

```text
V4.7B exact Linux socket and governed clock authority
  -> V4.8A exact projection-clock and construction binding
  -> V4.8B loaded chronyd process/configuration provenance
  -> V4.9 exact TLS 1.3 + WebSocket Sans-I/O driver
  -> provider conformance, crash campaigns, and no-trading soaks
```

TLS is not useful as a promotion boundary while another caller can choose the
durable chronology or substitute the implementation that allegedly produced
the TLS facts.

## 3. Frozen V4.8A contract

### 3.1 Reference and operational profiles

The ordinary projection constructor retains its deterministic `clock=` seam
for reference replay and tests. That path is explicitly non-live. A live
runtime must use the sealed Linux factory, which binds the open projection
instance to its exact `LinuxSocketOwnerV4` authority before claiming the
application writer fence.

Binding is:

- one-shot for the open store instance;
- restricted to its binding process and thread;
- established before the application writer fence;
- never restored from SQLite metadata;
- live only for the exact promotion-eligible Linux owner type;
- checked again when the runtime is constructed.

SQLite genesis metadata is created before an operational owner exists. Its
creation timestamp is identity/bootstrap metadata only; it cannot authorize a
session, subscription, H1 decision, or outbound write.

### 3.2 One sample per mutating transaction

For each governed mutation:

```text
clock_source.sample()
  -> exact ClockEvidenceV4 validation
  -> remember sample as consumed
  -> BEGIN IMMEDIATE
  -> same-domain monotonic expiry probe
  -> validate active writer-fence epoch
  -> use evidence.sampled_at for every generated timestamp
  -> replay and invariant checks
  -> same-domain monotonic expiry probe
  -> COMMIT or ROLLBACK
  -> clear transaction-local evidence
```

Sampling failure or invalid evidence occurs before `BEGIN IMMEDIATE`, so it
cannot leave a partial SQL mutation. A valid sample is still consumed when a
later fault causes rollback: reusing it would claim that a later transaction
was observed inside an earlier clock bracket.

The two deadline probes read only the already-bound monotonic domain. This is
necessary because `BEGIN IMMEDIATE` can wait for another writer and a valid
sample can otherwise expire before it is used. A failed or regressing probe
rolls the transaction back. `KeyboardInterrupt`, cancellation-style base
exceptions, and ordinary exceptions all take the explicit rollback path.

### 3.3 Evidence admission

The projection accepts only the exact `ClockEvidenceV4` type and requires:

- `synchronized=True`;
- the bound clock-source manifest ID;
- the bound monotonic-clock domain ID;
- uncertainty no greater than the bound maximum;
- a strictly positive lifetime no greater than the bound maximum;
- a monotonic bracket beginning strictly after the previous consumed bracket;
- a non-regressing wall sample;
- process/thread continuity.

The live profile additionally requires a positive-width monotonic bracket,
clock resolution, observation digest, and selectable-source count. The Linux
clock source performs the stricter boot, namespace, chrony-artifact, freshness,
source-count, uncertainty, and wall-versus-`CLOCK_BOOTTIME` checks defined by
V4.7B.

### 3.4 Exact live-construction identity

The sealed factory requires exact instances of:

- `PhysicalProjectionStoreV4`;
- `PhysicalTransportWriterLeaseV4`;
- `OperationalDeploymentAdmissionV4`;
- `PhysicalTransportRuntimeConfigV4` when supplied.

The future promotion-eligible owner must be the exact
`LinuxSocketOwnerV4` type with the exact pinned driver type. The projection
stores that owner object as its clock source. Runtime construction checks both
object identity and the source/domain commitment from the owner snapshot.
The owner accepts only the exact live clock implementation or the exact named
deterministic harness; an arbitrary subclass cannot override clock evidence.

Checking object identity is intentional. Two owners can share one policy,
kernel boot, and time namespace while controlling different sockets. Equal
clock identifiers therefore do not prove equal transport authority.

V4.8A leaves `LinuxSocketOwnerV4.is_live_profile` false for every current
structural driver. V4.9 must change this only for the exact reviewed
TLS/WebSocket implementation.

### 3.5 Session evidence boundary

The existing test runtime may still accept deterministic signed session
fixtures. A live runtime cannot accept a caller-built
`TransportSessionAttestationV4`. It aborts the presented owner and fault-latches
instead; it always aborts its exact retained authority as well, even if the
caller presents a decoy owner. The live-bound projection independently rejects
the same public append operation, so wrapping it in a downgraded test runtime
cannot bypass the rule. V4.9 must replace this with an internal API where the
exact retained driver supplies sealed handshake observations and the runtime
derives the session record itself.

## 5. Verification and falsification

The dedicated V4.8A tests establish:

- one sample supplies the fence claim and all receipt/batch times generated by
  one transaction;
- overlapping monotonic brackets and wall regression cannot release an active
  fence;
- wrong source, wrong domain, excessive uncertainty, unsynchronized evidence,
  zero lifetime, and overlong lifetime fail before SQL mutation;
- source failure is wrapped as a projection-clock error;
- evidence expiring between lock acquisition and commit causes a complete
  rollback;
- base exceptions cannot leave an open or partially committed transaction;
- invalid binding arguments cannot leave a half-bound store;
- binding is one-shot, process/thread-bound, and absent after reopen;
- arbitrary clock objects cannot enter live binding;
- forged clock subclasses are rejected;
- structural drivers cannot create a live bundle;
- fake journals and leases are rejected before socket ownership transfers;
- a forged live-looking authority and direct live-token use are rejected;
- test-profile downgrade and live wall-clock/entropy seam injection are
  rejected;
- direct live projection session append is denied, and live rejection aborts
  both the exact retained owner and a presented decoy.

The broader physical/operational suite and full repository suite are required
to remain green before this slice is accepted. Passing local tests does not
replace the still-required process-provenance, real-driver, provider, crash,
and soak evidence.

## 6. Research basis

The design follows SQLite's documented rule that a write transaction is
serialized and `BEGIN IMMEDIATE` starts it immediately, while atomic commit is
provided by the database transaction rather than by an external clock query:
[SQLite transactions](https://www.sqlite.org/lang_transaction.html) and
[SQLite atomic commit](https://www.sqlite.org/atomiccommit.html).

The monotonic domain remains Linux `CLOCK_BOOTTIME`, which includes suspended
time and does not jump when wall time is changed:
[`clock_gettime(2)`](https://man7.org/linux/man-pages/man2/clock_gettime.2.html).
Chrony machine-readable tracking/source evidence and command-socket behavior
come from the official [chronyc 4.8](https://chrony-project.org/doc/4.8/chronyc.html),
[chronyd 4.8](https://chrony-project.org/doc/4.8/chronyd.html), and
[chrony.conf 4.8](https://chrony-project.org/doc/4.8/chrony.conf.html)
documentation.

The next driver is deliberately constrained to a network-I/O-neutral TLS
engine. Python documents `SSLObject` plus `MemoryBIO` and `SSLContext.wrap_bio`
for TLS without socket ownership:
[Python SSL memory BIO support](https://docs.python.org/3/library/ssl.html#memory-bio-support).
The official websockets 16.0 Sans-I/O guide makes the integration responsible
for network I/O, serialized protocol access, feeding received data, and
draining generated output:
[websockets Sans-I/O integration](https://websockets.readthedocs.io/en/16.0/howto/sansio.html)
and [client protocol reference](https://websockets.readthedocs.io/en/16.0/reference/sansio/client.html).
TLS 1.3 and WebSocket masking/control requirements remain governed by
[RFC 8446](https://www.rfc-editor.org/rfc/rfc8446.html) and
[RFC 6455](https://www.rfc-editor.org/rfc/rfc6455.html).

These sources justify the mechanisms and protocol constraints. They do not
show that this project has market-prediction edge or that one exchange's live
behavior will match local fixtures.

## 7. Diagnostic-host result

The current host runs `chrony.service` through a distribution starter script
with `-F 1`. Its configuration includes dynamic source directories. The
desktop user can observe basic process arguments but cannot read the protected
process executable/namespace evidence or access the configured root-only
chronyd command socket. Consequently:

- on-disk executable/configuration hashes do not prove what the already-running
  daemon loaded;
- the exact launcher, service environment, dynamic-source set, and command
  socket peer are not yet sealed into one launch-time attestation;
- the host remains non-promotion-ready and must continue to fail closed.

V4.8B subsequently selected a dedicated prospective launch rather than
retrospective attachment. It retains the unit file and executable, rejects
dynamic include/source-resolution state, assembles one literal-IP-only static
configuration, validates the pinned parser's output, and binds the exact
process/socket instance and authenticated read-only transcript. The narrower
implemented result and its remaining systemd-manager, peer-containment,
clock-exclusivity, privileged-integration, and durable-API gates are frozen in
`v4_8b_loaded_chronyd_provenance_protocol_freeze_2026-07-15.md`.
